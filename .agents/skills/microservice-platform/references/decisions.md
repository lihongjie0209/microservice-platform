# Architecture Decisions

## Repository model

- The workspace is a coordination directory; services, contracts, shared libraries, and delivery assets remain independently versioned repositories.
- Initial platform services are identity, tenant, and authorization.

## Interfaces

- Frontend clients use service-owned POST+JSON APIs with a uniform response envelope.
- Services use versioned gRPC contracts from `platform-protos` for synchronous calls.
- Domain events use NATS JetStream with versioned subjects and shared envelopes.
- All `platform.>` domain subjects belong to the single `PLATFORM_EVENTS` JetStream stream. Services may idempotently provision the same stream; independent processing is represented by durable consumer names, never overlapping streams.
- The only platform event wire format is protobuf `platform.common.v1.EventEnvelope`; JSON broker envelopes are not allowed on `platform.>` subjects.
- Events owned by an application carry `application_id` in the shared `EventEnvelope`, in addition to `tenant_id`. Application-scoped consumers such as webhook delivery planning filter on both fields before reading domain payloads or creating state, and fail closed for legacy events without application scope. Producers derive the value from authoritative persisted state rather than caller-supplied metadata.
- Shared JetStream consumers use explicit double acknowledgement, bounded `MaxAckPending`, handler deadlines, delayed exponential redelivery and a finite delivery count. Final failures and malformed envelopes are published as `platform.common.v1.DeadLetterEvent` before the source message is terminated; a dead-letter event is never recursively dead-lettered.
- `identity-service` is the only platform token issuer. Other services verify EdDSA access tokens from its JWKS endpoint through `platform-go`, validating issuer and service-specific audience; they never expose credential login endpoints.
- `scheduler-service` dynamically invokes allow-listed unary internal RPCs using Server Reflection plus JSON-to-Protobuf descriptors. It never compiles downstream business client stubs; its own management server still implements the versioned `platform.scheduler.v1` contract normally. Jobs and executions are owned by `tenant_id + application_id`; every mutation/read by ID authorizes the persisted scope, scheduled runs revalidate the active application grant, and downstream calls carry scope metadata. Legacy jobs with unknowable ownership are disabled and excluded until an operator performs an authoritative backfill.
- `workflow-service` uses Temporal for durable timers, human-task waits, retries, and reverse-order compensation; NATS JetStream remains the platform domain-event bus. A business transaction writes workflow state and a runtime command to its transactional Outbox, and an idempotent JetStream consumer starts, signals, or cancels Temporal so a Temporal outage cannot lose a committed command.
- `search-service` owns only an OpenSearch projection, never source-of-truth records. Owning services publish versioned search-document upsert/delete events through their transactional Outbox; a protected batch gRPC API exists only for idempotent rebuild/backfill. Search visibility is expressed with stable tenant/user/membership/role/service-account tokens generated by owners and intersected with server-derived caller tokens, never caller-provided roles. Caller role tokens are resolved from authorization-service, JWT tenant scope is enforced before querying, permission-protected documents cannot use tenant-wide visibility, and source versions drive monotonic idempotent OpenSearch writes. Application-filtered Search/Suggest batch-verify every requested application grant; Get verifies the application stored on the fetched document. The normal application page always supplies its selected application, while an intentionally separate global-search capability may submit several explicitly authorized applications.
- `swagger-service` aggregates OpenAPI documents without a database. Local environments use static sources; Kubernetes uses a read-only `client-go` Service SharedInformer selected by `platform.swagger/enabled=true`. It exposes protected POST+JSON console APIs in addition to the standalone UI. The console forwards the authenticated user's multi-audience JWT, renders fixed-version Swagger UI assets hosted by the service, and caches only validated documents; it does not use an iframe or a second token store.
- Application catalog, menu releases, and tenant application grants initially belong to one `application-service`. Tenant facts remain in tenant-service and permission decisions remain in authorization-service; menu-service and entitlement-service are split only when their lifecycle and team boundaries become independently complex. Initial platform applications and page menus are reconciled by a Cobra/Viper `platform-bootstrap` CLI through application-service APIs, never seeded by cross-schema SQL or startup auto-mutation. Its manifest is declarative and rerunnable; undeclared resources are preserved unless a future explicit prune workflow is requested.
- Application catalog mutation, menu draft/publication, and tenant-application grant mutation are reserved-platform operations authorized against `__platform__`. Tenant users use a separate tenant-scoped grant list for their application launcher; platform administrators use a dedicated management list that records a successful platform decision before domain code permits a target tenant different from the JWT-selected tenant. Menu permission scopes mirror these backend boundaries.
- `service-registry-service` owns ephemeral application-level instance leases and metadata discovery. Redis Lua atomically maintains lease ownership, TTL, indexes, revisions, and a resumable Redis Stream; Kubernetes Service/DNS remains the underlying network discovery layer. The platform does not implement its own consensus system.
- `dictionary-service` is the unified dictionary entry point. Static dictionaries remain persisted locally; dynamic providers register each live instance with generic registry metadata. `platform-go/serviceregistry` supplies cached discovery, bounded stale snapshots, reconnect/re-register behavior, weighted selection, and passive ejection. Dictionary-specific capability semantics never enter the registry contract.
- Dictionary definitions use the same three explicit scopes as configuration: platform defaults, tenant defaults, and application overrides. Management lists are exact-scope queries, while Get/Query/Tree/Resolve use application > tenant > platform precedence. Application overrides require an active grant; dynamic provider registrations remain platform-global but receive the original caller tenant/application scope for provider-side filtering.
- Apache APISIX is the platform's external API gateway. In Kubernetes, APISIX Ingress Controller discovers Service EndpointSlices from explicitly enabled `ApisixRoute` resources; application-level registry discovery is not placed on the public traffic path. Production hosts use `<service>.<base-domain>`, while non-production uses `<service>.<environment>.<base-domain>` with an independent APISIX release, ingress class and ZeroSSL DNS-01 wildcard certificate per environment.
- `metering-service` owns a platform-global meter catalog and immutable usage facts scoped by `tenant_id + application_id`. It verifies active tenant-application grants through application-service; ingestion is idempotent by event ID, corrections are append-only adjustment facts, and a mixed-scope batch emits one transactional Outbox envelope per tenant/application pair. PostgreSQL/Kingbase facts are time-partitioned. Billing consumes the versioned metering API/events and never reads the metering schema. Aggregate result pagination and dimension filtering execute in the database rather than paging raw facts into application memory.
- `billing-service` owns a platform-global plan and usage-price catalog. Subscriptions, invoices, payment attempts, and refunds are scoped by `tenant_id + application_id`, verify the active tenant-application grant, and derive child scope from persisted parents. Each tenant application has its own active-subscription claim; invoice calculation queries metering with both scopes, and commercial events carry both scopes in the shared envelope.
- `notification-service` owns templates and delivery attempts within `tenant_id + application_id`. Template identity, delivery idempotency, receipt lookup, frequency-limit keys, and list/get filters all include both scopes. The service verifies the tenant-application grant through application-service; workers and status events derive application scope from the persisted delivery. Existing installations use an expand/backfill/contract migration and must never invent a default application for legacy notifications.
- `file-service` owns file metadata and upload sessions within `tenant_id + application_id`; object keys include both scope segments. Upload idempotency, metadata queries, presigned upload/download authorization, multipart lifecycle, scanner receipts, deletion, and status events all preserve that scope. Object-storage endpoint and bucket configuration remain platform infrastructure, while file ownership remains application data. Existing rows require an authoritative expand/backfill/contract migration.
- `config-service` models configuration as three explicit scopes: platform defaults use empty tenant and application IDs, tenant defaults use a tenant ID with an empty application ID, and application overrides use both IDs. Resolution evaluates application, tenant, then platform candidates and applies rollout independently at each level so a missed override can fall back. Only application overrides require an active tenant-application grant. Legacy rows safely migrate to an empty application ID because the previous contract represented only platform and tenant defaults.
- `audit-service` preserves an optional `application_id` from the authoritative event envelope or recording request. User queries and exports require `tenant_id + application_id` and verify the tenant's active grant through shared `appaccess`; Get verifies the application stored on the record. An empty application remains valid for tenant- or platform-level actions and tenant-wide audit is restricted to explicitly authorized service identities, never enabled by a browser omitting scope. Event/PSK ingestion remains service-authorized so revocation cannot erase compliance history.
- `rule-service` owns application-scoped rule sets, immutable versions, validation, publication, and deterministic evaluation. Every rule identity and query is scoped by `tenant_id + application_id`; the service verifies the tenant application grant through application-service and stores both fields on rule sets and versions. Rules are ordered CEL boolean conditions with JSON-object results and a default result; arbitrary scripts and implicit cross-service data reads are forbidden. Facts are supplied explicitly by callers, published definitions are canonicalized and checksummed, and publication emits a transactional Outbox event carrying both scopes on `platform.rule.rule-version.published.v1`.
- `data-export-service` owns export jobs within `tenant_id + application_id`. Application scope participates in idempotency, list/get/mutation predicates, object keys, provider stream requests, and event envelopes; every job creation and access verifies the active tenant-application grant. Legacy jobs with no authoritative application mapping are not exposed through application APIs, and unfinished legacy work is canceled during migration pending an operator-controlled backfill.
- `import-service` owns dataset access and import jobs within `tenant_id + application_id`. Application scope participates in idempotency, every lifecycle predicate and worker claim, object keys, Provider describe/validate/apply requests, and event payloads/envelopes; catalog and job access verify the active tenant-application grant. Legacy rows with unknown ownership remain hidden, and unfinished work is canceled during migration until an authoritative backfill assigns the real application.

## Frontend

- `platform-console` is an independently versioned, single Vue SPA based on Soybean Admin Element Plus. It hosts both platform administration and future business-system modules; it is not a microfrontend host.
- Browser clients call only public HTTP service endpoints on service subdomains. They hold Identity access/refresh tokens in `sessionStorage`; browser bundles never receive PSKs, mTLS credentials, internal gRPC access, or other service secrets.
- The console obtains navigation from the active tenant's application grants and published application menus. Backend menu component strings are data only and are never dynamically imported; every concrete frontend page must be registered in a local allowlist.
- Console service addresses are public runtime configuration injected into `platform-config.js`. Development uses a checked-in local default; container startup renders the file from `PLATFORM_*_URL` values, and production configuration requires HTTPS.
- Swagger 2 documents remain service owned. The console converts their immutable commit-SHA source URLs to OpenAPI 3 and generated TypeScript declarations; CI regenerates and compares them so documentation/model drift is visible in review. A mutable `main` URL plus a revision query is not a pin because CDN edges may serve different commits.
- The post-login home is a tenant-aware application launcher. It restores only active session-scoped tenant/application choices, lists grants from application-service, and enters a valid published default page; server-side services remain authoritative for every permission decision.
- Frontend source modules are organized by user-facing application (`src/apps/<application>`), not by backend service. A module may compose several service-owned HTTP APIs; published menu `component` values are stable page keys such as `platform-admin.users`, resolved only through the local application page registry. Resolution also requires the page-key namespace to match the authoritative application code, so one application's menu cannot mount another application's page.
- Every generated application route carries its locally derived application ID. The authenticated route guard synchronizes that ID into the session-scoped platform store before rendering, so direct URLs and cross-application menu navigation cannot execute a page with stale application context.
- Frontend request adapters use the shared `applicationScope` helper whenever an endpoint is application-scoped. Domain modules must not maintain subtly different tenant/application pairing helpers; the common helper fails before transport when either value is absent.
- Application-scoped pages clear rows, selections, drawers, dialogs, and preview state when tenant or application changes, so stale resources from the previous scope cannot be mutated through an already-open editor.
- Refreshing tenant navigation reconciles open and persisted tabs against the newly installed route set; an invalid active tab falls back to the application launcher. Tabs from revoked grants or a previous tenant are never retained as navigable UI state.
- Application-scoped backend resources carry an immutable application ID through parent and child models, lookup keys, list filters, and mutation requests. Services verify the tenant's active grant through `platform-go/appaccess` and application-service; browser-selected application IDs are never trusted as authorization evidence.

## Data

- Services never share tables.
- Online service-to-service data access uses APIs or events, never cross-schema SQL. Reporting/OLAP builds separate read models through CDC/events/exports; direct OLTP reads are exceptional, read-only, and architecture-reviewed.
- PostgreSQL is the default database. The initial services share database `platform` with per-service roles, schemas, and migration tables.
- Kingbase follows the same schema isolation model when selected.
- MySQL uses per-service database names.
- All mutable persistent tables use `version BIGINT NOT NULL DEFAULT 1` and the four platform audit columns: `created_at`, `updated_at`, `created_by`, and `updated_by`. Actor attribution is passed explicitly from shared authenticated context through application and repository layers.
- Updates and soft deletes use expected-version optimistic concurrency. Distributed locks are reserved for cross-resource/cross-system invariants and use the narrowest stable resource key.
- PostgreSQL strings default to `TEXT`; bounded types are reserved for genuine domain constraints. Time instants use `TIMESTAMPTZ`, with database/connection presentation set to `Asia/Shanghai` (UTC+08:00).
- High-growth tables have explicit partition, retention, and archive policies. Service migrations own declarative partitioning; deployment/DBA automation may use `pg_partman` without making it mandatory for service startup.
- `docs/high-growth-data-policy.md` is the authoritative capacity inventory. A global uniqueness or foreign-key invariant takes precedence over premature time partitioning; services use bounded terminal-state cleanup until the identity contract can include a partition key.
- Kubernetes service deployments run database migration in a Pod init container by default, so configuration/Secret resolution precedes migration and migration success precedes API startup. Concurrent replicas rely on the shared PostgreSQL advisory-lock migration guard. A hook Job is opt-in only when its ConfigMap and Secret are provisioned independently before the release.

## Shared code

- Stable cross-cutting Go code is extracted into `platform-go`.
- Domain code remains local even if structs look similar across services.
- Shared authentication/authorization interceptors, principal/audit context, and Redis distributed locking live in `platform-go`; services provide policy/verifier implementations and domain authorization requirements.
- The shared gRPC Authorizer maps a user to its tenant membership (never its global user ID), maps service/system callers to service-account subjects, forwards the caller credential, applies a bounded deadline, and preserves the distinction between an explicit denial and an unavailable decision service. Production services fail closed when authorization is enabled but its named upstream is absent.
- Platform-scope administration uses reserved authorization namespace `__platform__`; global users map to the protobuf `USER` subject while service callers remain `SERVICE_ACCOUNT`. Tenant-scope decisions continue to map users only through memberships. Authentication lifecycle and identity fact RPCs must not depend on an authorization decision, while identity/session/service-account administration does.
- The reserved platform super-admin role and wildcard permission are installed by authorization-service migrations without any subject binding. The first user or break-glass service account is granted only through the explicit, idempotent `bootstrap-admin` CLI (normally an operator-invoked Kubernetes Job); API startup never auto-grants or restores administrators.
- A new tenant's authoritative owner membership receives the reserved tenant-local `tenant-owner-admin` wildcard role through authorization-service's durable `TenantCreated` event projection. Event processing, reserved permission/role/link/binding creation, processed-event recording, and policy-version bump share one transaction and tolerate redelivery. This is tenant-local bootstrap, not a platform-super-admin grant; no other member is implicitly privileged.
- authorization-service protects its permission, role, role-permission, and binding management operations with an in-process Authorizer over the same decision domain. `ScopePrincipal` selects tenant membership when present and reserved platform user/service-account otherwise. Decision, cache-invalidation, health, and operational methods are explicitly excluded so authorization never recursively authorizes its own `Check` call.
- authorization-service also binds every interactive management operation to resource ownership inside the domain service: tenant users may access only their JWT tenant, unscoped users only `__platform__`, and ID-based updates/revocations verify the persisted entity tenant before mutation. Trusted service/system identities may orchestrate explicit tenant scopes only after their separate service authentication and authorization succeeds.
- Machine lifecycle RPCs already protected by PSK/mTLS and capability tokens (for example provider registration, heartbeat, and unregister) do not also require a tenant-membership authorization decision. Human/admin management and read operations remain centrally authorized; coverage tests explicitly enumerate both protected and intentionally excluded methods.
- Tenant bootstrap/self-service operations that necessarily precede an active membership (create a tenant for the authenticated user, accept invitation, list the caller's tenants) remain authenticated and enforce their domain ownership rules without a tenant-scoped RBAC call. Every tenant-owned management method also compares the request or persisted resource tenant with the trusted JWT tenant after RBAC; ID-based operations load ownership before mutation. The global tenant directory is reserved-platform administration and carries a process-local successful-decision marker. Tenant fact RPCs used by authentication/authorization (membership validation/read and organization-scope resolution) must not call authorization-service recursively; protected and intentionally excluded methods are both enumerated in tests.
- Global error codes and transport mappings live in `platform-go`; domain services may define messages/details but must not allocate duplicate numeric codes locally.
- Reflection-based unary JSON-to-Protobuf invocation shared by scheduler and workflow orchestration lives in `platform-go/dynamicgrpc`. Services provide only an allow-listed, authenticated connection registry; runtime targets and credentials never come from persisted task rows.

## Frontend

- The console is application-first: the launcher lists every application granted to the selected tenant, but the authenticated shell mounts routes, side navigation, breadcrumbs, tabs, and menu search for exactly one selected application. Platform-wide administration is itself a separately granted platform application; never flatten menus from multiple applications into one workspace.
- Every selected application receives a console-owned overview route under its application namespace. It may summarize only the application's already authorized published navigation and remains usable when no business menu has been published; business pages and default routes still come from application-service.
- External application menus accept and open only absolute HTTP(S) URLs without embedded user information. application-service enforces this at the write boundary and the console fails closed again for legacy catalog data.
- Password login creates an unscoped interactive session. Selecting a tenant is an explicit token exchange owned by tenant-service and identity-service together: tenant-service validates the current user's persisted active membership, then a trusted service call asks identity-service to persist tenant/membership on the same session and issue the scoped token. Refresh inherits persisted session scope. Direct user calls to `IssueTenantToken` are forbidden, and concurrent console selections are serialized.
- Every protected application menu carries both `permission_code` and `permission_scope`. `tenant` decisions use the selected JWT membership; `platform` decisions use the same authenticated user's reserved `__platform__` subject, while still requiring a valid selected-tenant token context. The console batches and filters by the tuple `(scope, code)`, never a cross-scope code union. Resource-dependent ABAC grants remain hidden because navigation has no authoritative resource facts. The console removes denied menu subtrees for usability; service-side authorization remains the security boundary.
- Menu permission selection uses authorization-service's dedicated current-principal catalog API. The service derives tenant membership or reserved platform user from the JWT, authorizes `authorization.permission/list` in that derived namespace, and only then searches active permissions. The generic administrative list API is not used as a browser lookup oracle, and a request-body `tenant_id` is never treated as authorization evidence.
- Interactive permission, role, role-permission, and role-binding administration has dedicated current-user endpoints for `tenant` and `platform` scopes. The server validates the selected tenant against JWT claims, derives the membership or reserved global-user subject, authorizes the requested action in that exact namespace, and stamps a non-forgeable request Context target used by domain ownership checks. Platform bindings accept only global users or service accounts; tenant bindings accept only memberships, groups, or service accounts. Generic gRPC/PSK management contracts remain compatible for separately authorized service orchestration.

## Testing

- Every feature has unit coverage.
- Infrastructure and service-owned adapters use Testcontainers integration tests with the `integration` build tag.
- A service test suite never requires another service. Outbound service clients use in-process fakes/bufconn/contract stubs; multi-service journeys live in a separate platform `system-tests` project.
- Bugs found manually or in integration tests are reproduced in a unit test first whenever the root cause can be isolated.
- Developer workstations run unit, race, vet, lint, generation, and configuration checks only. Testcontainers integration and platform system journeys run in GitHub CI; pushes do not block ongoing development, and completed CI is checked opportunistically at safe task boundaries.
